### 2026-10-19の追加指定：Issue #38（D052）

[Issue #38](https://github.com/jphacks/tka_2608/issues/38)とユーザーの実装依頼による変更。Figmaは編集していない。以下の指定を過去の表示・戻る動作より優先する。

- OSのShieldからは相談チャットを直接開く。その相談・やること選択・ふりかえりを閉じるとき、アプリ内に制限画面を新規生成せずホームへ戻る。既存のアプリ内制限画面から来た場合だけ、その既存画面へ戻る。
- 同じ対象のOS要求を再受信しても、進行中の相談・やること選択・取り組み・ふりかえりを作り直さない。
- 他アプリ上のShieldは固定の背景色を使い、端末の外観で変わるMaterialを使用しない。実機のダークモード表示は別途確認が必要。
- 使用時間一覧の「一時的に利用できます（残り…）」を削除する。相談で解除に成功したときの1回の案内は維持する。
- アプリ別上限Sheetの見出しは「1日の上限を設定」。アプリ名は見出しに組み込まない。編集対象の名前・アイコンは行に残す。
- ふりかえりの報酬内訳の最終行は、アプリ名を含めず「合計 +○分」とする。追加先選択後と完了時の「ホーム画面から○○を開いてね」は削除する。追加先の選択と成功時のアリのセリフは維持する。
- 入力欄タップで相談からやること選択へ変わるという報告は、修正前のシミュレータUI操作では未再現。キーボード表示と文字入力で相談画面が維持されることを確認し、入力処理への推測による変更は加えていない。

### 2026-10-19の追加指定：Reportへの使用時間表示の統一（D051）

ユーザーが「各アプリの使用時間と遊んだ時間を統一し、約1分ごとに反映したい」と指定し、Report方式の実装を依頼。本節はD050の目盛り通知による使用量表示を置き換える。

- 通常版の各アプリの使用分数・バー、上部の遊んだ時間、週次の遊んだ時間はすべてReport拡張が実使用時間から描画する。画面点灯時間（`ActivitySegment.totalActivityDuration`）ではなく、アプリ単位の`ApplicationActivity.totalActivityDuration`を集計する。
- 各アプリの時間区間を秒単位で足してから分に切り捨てる。上部の合計は、その表示分数の和にする。
- 今日の集計期間は端末の現地時刻で朝4時〜現在、対象は選択中のアプリと現在の端末。週次も同じ朝4時境界を使う。アプリの導入・選択前の当日の使用分もOSが返す範囲で含む。
- 全Reportで共通の取得期間・更新世代を使い、前面表示中に約60秒ごと、復帰時と使用時間画面を開いたとき、下に引いたときに再取得を試みる。OS側のデータが必ず毎分更新される保証はない。別々のReport描画が更新中に一時的にずれる可能性もあり、同じ瞬間のスナップショット一致までは保証しない。
- 上限・追加時間と取り組み時間だけを本体からApp Groupへ入力として保存し、Reportは読み取る。Reportから実使用時間を本体へ書き出さない。上限入力を読めなかったバーは灰色で表し、使用0として塗らない。
- 上限変更のボタンとSheetは本体に残す。制限・一時利用の終了と再制限はMonitorの閾値通知で担当し、Report表示だけで解除しない。D050の使用時間目盛りイベントと本体側の推定値の取り込みは撤去。
- 未選択時は0分、未認可時は取得不能を示す「—」。PersonalDemoの既存固定値は維持。実機でのReport更新遅延、App Group入力の読み取り、表示・操作の確認が必要。

### 2026-10-19の追加指定：Issue #33（D046）

[Issue #33](https://github.com/jphacks/tka_2608/issues/33)とユーザーの実装依頼を優先する。以下はコードへの変更であり、今回Figmaは変更していない。下記の過去のFigma記録やIssue #13の足し算表示、旧ルール画面より本節を優先する。

- 初回の許可画面からスクリーンタイム許可成功後の案内を削除。プライバシー説明の手動改行を削除し、画面幅で自然に折り返す。
- アプリごとの基本上限は0〜24時間、5分刻み。時間は「22時間25分」も1行に収める。
- 使用時間の「アプリを追加・外す」から標準ピッカーを直接開き、閉じたときに選択を保存する。中間の「アプリを追加」画面・適用ボタンを撤去。既存アプリの上限は保ち、全解除も保存する。
- 設定トップに「リマインダーのリスト」「1日に相談できる回数」を置く。別のルール画面は撤去。相談回数は1回以上で編集し即時保存する（初期3回、全アプリ合計、朝4時切替）。変更しても今日使った回数は消さず、開始時・利用枠発行直前に新しい回数を検査する。PersonalDemoの回数無制限は従来どおり。
- OSのShieldに本体と同じ `shield_ant` の画像、「やることやろう！」「ちょっとアリさんに相談してみない？」を表示。対応OSでは「アリに相談する」「閉じる」の2ボタンとし、相談は対象のチャットへ直接進む。iOS 26.5未満は本体自動起動ができないため手動の案内を残す。自由なSwiftUI画面を他アプリ上へ重ねる実装ではない。
- 相談の最初の発言は「どうして今このアプリを開きたいのか、教えてくれる？」。チャット内のアプリ名は通常のTextにし、OSのトークン名ラベルを混ぜない。名前を取得できない実アプリは「このアプリ」とする。
- チャット最下部の操作ボタンは文字だけ・高さ50ptで統一。許可後のボタン押下で既存ポリシーを再検査して利用枠を発行し、その成功後にだけ「（アプリ名）が使用可能になりました」「（実際の許可分数）分間使えます」を1回表示する。固定の1分付与に変更する指示ではないため、許可時間の範囲・しきい値は維持する。
- 使用時間の「ホーム画面から開いてください」を削除。「使用 / 合計上限分」にし、元の上限と追加分の合計を分母に表示。利用可能分は緑（Issue #35で薄い茶色に変更）、使用済みは赤、基本上限と追加分の境界を縦線で示す。追加分がない場合は境界線を出さない。
- ホームのやることを押すと、その行内に「このやることをはじめる」ボタンを出す。確認ダイアログ・質問文は削除。「やることに戻る」に表記を統一する。
- ふりかえりの選択肢と選択後の発言を「終わった」「まだ途中」にする。

### 2026-10-18の追加指定：Issue #25（D040）

以下は[Issue #25](https://github.com/jphacks/tka_2608/issues/25)による実装への追加指定。下記のFigma確認記録と異なる場合はこちらを優先する。今回Figma自体は変更していない。

- 表示するプロダクト名は「ToDo〆～る」。初期画面と通常版・PersonalDemoのホーム画面上のアプリ名を合わせる。
- 初回設定の通知の項目を削除する。通知の実装は後回し。「アプリを追加」の「使う時間は、戻った画面で調整できます。」も削除する。
- 設定のデータ操作は「データをリセットする。」。確認ダイアログで削除範囲を説明してから実行する。
- 制限画面の見出しは「やることやろう！」。やることがない場合は「一緒に頑張ろう！」。読み込み中・権限なし・取得失敗は従来どおり区別する。
- タスク選択後は「えらい！頑張るほどアプリを使える時間が増えるよ。いってらしゃい！」。相談後の見送りでも同じ文言を使い、進み具合への回答前も報酬の細かい数字を出さない。報酬自体の計算は維持する。
- 使用時間画面の「上限まで進める」アイコンは、上限到達後も表示してレイアウトを保つ（Issue #35で削除）。
- アリ度はD011の取り組み時間÷目標時間、キリギリス度は100％からアリ度を引いた値。表示は既存どおり0〜100％、5個のドットに％も併記する。現コードで固定値は確認できず、目標到達後は100％／0％になる。計算・日次切替は合成記録で検証し、報告された実機状態の原因特定とは区別する。

| 獲得した利用時間                                        | **アプリ時間**。「アプリ時間に○分追加」。貯めて持ち越す表現は使わない（D034） |

「制限」と「上限」を混同しない。上限は時間の設定値、制限はアプリを利用できない状態。内部の処理説明では「制限の一時解除」を使ってよいが、上限を増やしただけでアプリが利用可能になったとは表示しない。本体・OS・拡張の技術上の区別や既存の識別子は、表示用語とは別に扱う。

Figmaには旧表記が一部残る。本書の画面名と文言は上表を適用した表記であり、Figma内の文字列をそのまま引用したものではない。たとえば「つい開くアプリと、使う時間」「やることを1つ完了したら」「どのアプリに使う？」と記載する。

## 4. AIとの対話・プロンプト案

### 対話の進め方

1. 最新のやることから、始められる候補を短く提示する。
2. アプリが今必要な理由を聞く。すでに説明された事情を繰り返し尋ねない。
3. やることの小さな一歩、別の確認方法、短時間のアプリ利用を状況に応じて提案する。
4. 本体が条件を検査し、制限の変更やアプリ時間の適用が成功してから確定文言を出す。
5. 実行後は進捗を確認し、本人の「完了にする」と元データの更新結果を区別する。
6. ホーム起点のふりかえりでは、獲得したアプリ時間の追加先を選んでもらい、成功した対象を明示する。

### システム指示の叩き台

### アプリに組み込んだ指示（`draft-03-app`、D036）

Issue #6で納得度を調整した版。本文は `todomeru_ios/todomeru_ios/Features/Persuasion/FoundationModelsPersuasionAI.swift` の `instructions(for:)` を正とし、ここには方針だけを書く。実モデルでの応答品質・再現性・応答時間は未評価。

- 固定の指示と採点例をセッションの指示にまとめ、しきい値・時間・往復数だけを `PolicyConstants` から埋め込む。定数を埋め込んだ後で1,800文字以内（テストで検査）。
- 対象アプリ名・やること一覧・発言数・会話履歴は毎回の入力データとして渡す。前回の納得度は渡さない。
- 納得度はD023の3要素を観点にした総合評価。0〜29は目的が不明、30〜69は今そのアプリでなくてよい・使う範囲があいまい、70以上は具体的な必要（時間を区切った休憩を含む）。発言回数・長さで加点しない。1通目から利用を提案してよい。
- 返答は1〜2文・120文字以内が目標。やること／アプリ／相談と呼び、「このアプリ」のときは固有名を推測しない。
- 出力は納得度・action・秒・やること番号を返答文より先に生成し、返答文はできた部分から表示する。許可はこれまでどおりUnlockPolicyで検査する。
- 履歴は直近8件・2,000文字以内（D021）。最新の発言は必ず渡し、それだけで上限を超える場合は渡す分を切り詰めて省略を明示する。前の会話を省いたときも入力に明示する。保存済みの原文は変えない。
- 点数帯・採点例は評価の目安。しきい値を変えるときは点数帯・採点例も見直す。
- 返答文が160文字を超えたら生成を打ち切り、続けて同じ文を1つにまとめて最大2文・120文字に整える（同じ文を繰り返して止まらなくなる対策。`ReplyText`）。

### 最初の一歩の提案（`first-step-01`、D037）

相談のあとで「やることを片付ける」からやることを選ぶと、アリが「始める前に、『○○』はいまどこまで進んでる？」と聞く。答えると、端末内AIがやることの名前・期限と答えから、5分以内にできる最初の一歩を1つ提案する（1〜2文・80文字以内が目標）。答えなくても「やることを始める」は押せる。本文は `todomeru_ios/todomeru_ios/Features/Persuasion/FirstStepAI.swift` を正とする。

- 渡すのはやることの名前・リスト名・期限と答えだけ。リマインダーのメモは渡さない。文書の中身や進み具合は読めないので、分からない部分は「たとえば」を付けた候補として出させる。
- 答えは200文字までに切って渡す。
- 端末内AIが使えない・失敗したときは、決まった一歩（「まずは『○○』に使うものを開いて…」）を出す。
- 「やることを選ぶ」画面（Shield・ホーム起点）には今回入れていない。取り組み実績は渡さない。
