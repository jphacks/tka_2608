# 共同開発と資料の更新

更新日: 2026-10-17。以下は少人数で使い続けるための運用案です。担当やPRルールの採用はチームで調整できます。

## 1. 作業開始時

1. `AGENTS.md`、`AI_CONTEXT.md`、`STATUS.md`、`DECISIONS.md` を読む。
2. `git status` と実ファイルを確認し、他の人の未完了変更を消さない。
3. 今回の担当範囲、接続するデータ・関数、成果物、検証方法を短く共有する。
4. 大会判断なら原文、iOS実装なら該当APIの最新資料と手元のSDKを確認する。

複数人のAIには、同じ最新版の共有文書と担当範囲を渡します。各チャットだけに仕様変更を閉じ込めず、判断と現在地をリポジトリへ戻してください。

## 2. 分担と統合の案

1日目午後はユーザー指定の2班方針で進めます。技術班は [ARCHITECTURE.mdの8節](ARCHITECTURE.md#8-午後の検討実装引き継ぎ)、UI・対話班は [UI_UX.md](UI_UX.md) に記入し、同書6節で両班の仕様を合わせます。人数配分と担当は [STATUS.md](STATUS.md) に記録します。初版の4枠案は実装時の役割を考える材料として残します。

- Xcodeプロジェクト、ターゲット、capability、共通型は先に責任者と編集範囲を決める。
- 担当ごとに独立したファイル・ブランチで進め、接続する型とエラー表現を先に合わせる。
- UIや会話のモックで先行する場合も、実データとモックを切り替える箇所を明示する。
- Mac／iPhoneによる実機確認を統合時に行い、Windows上の編集だけでiOS動作確認済みにしない。
- 当日の動く経路を小さく保ち、統合できた単位で検証結果とcommitを記録する。

ブランチ名、レビュー人数、CIの採否は未決定です。ここに書いた案を、未合意の必須手続きとして作業の停止理由にしないでください。

## 3. 完了の記録

AI・人間とも、変更時は「何を変えたか」「何を確認したか」「何が未確認か」「次の担当が何をすればよいか」を残します。

```markdown
### 作業の引き継ぎ

- 日時（JST）・担当:
- ブランチ・commit・対象ファイル:
- 完了したこと:
- 実データ／モックの範囲:
- 検証方法・結果・端末条件:
- 未解決の問題:
- 変更した判断・関連するD/P/Q/V番号:
- 次の一手:
```

実装状態は `STATUS.md` の対応行を更新し、完了した項目に証拠を付けます。「APIが公式に存在する」と「端末で動いた」を同じ完了欄にまとめないでください。

## 4. どのファイルを更新するか

| 起きたこと | 更新する場所 |
| --- | --- |
| ユーザーの追加要求・対象ユーザー・価値・MVP変更 | AI_CONTEXT.md、DECISIONS.md、必要ならREADME.team.md |
| 技術選定・実機で分かった制限 | ARCHITECTURE.md、STATUS.md、採用判断ならDECISIONS.md |
| UI文言・画面遷移・対話プロンプト | UI_UX.md、STATUS.md。採用判断はDECISIONS.md、技術との接続はARCHITECTURE.md |
| 新しい運営案内・締切・賞の更新 | sources/、HACKATHON.md、STATUS.md、README.team.mdの直近節目 |
| 担当決定・機能完成・統合失敗 | STATUS.md、必要ならDECISIONS.md |
| セットアップ確定 | STATUS.mdの手順欄。長くなったら新しいSETUP文書を追加して入口からリンク |
| 引用の誤りや要約の誤認を発見 | 要約側を修正し履歴を残す。受領原文は書き換えない |
| 今回の制約の変更をユーザーが明示 | AGENTS.md、DECISIONS.mdと関連資料 |

日付・担当・根拠を更新し、古い記述を読者が現状と取り違えないようにします。細かい現在地は `STATUS.md` を正として、概要に同じ詳細を大量に複製しない方針です。

### AQ項目の更新（ユーザー指定）

ARCHITECTURE.mdのAQ一覧には、未解決の問いだけを残します。仕様の決定・修正・スコープ除外を反映するたびに、解決した部分を削除してください。行全体が解決したら行を削除し、一部が残る場合は残った問いだけに書き直します。採用仕様は設計本文、判断の履歴はDECISIONS.mdへ記録します。AQ番号は振り直さず、削除した行への参照は採用仕様の記載先へ更新します（D017）。

## 5. 原文を追加・更新する手順

1. 新しい資料を `docs/sources/YYYY-MM-DD-種類.md` 等の別ファイルで保存する。同日複数なら連番を付ける。
2. 出典の題名、URLまたは受領方法、取得日（JST）、対象年・会場、全文か抜粋か、取得／照合状態を `sources/README.md` に追記する。
3. 元の文字列と改行を保つ。誤字や重複を修正する説明は別ファイルへ書く。PDF等からの抽出なら抽出したことと確認範囲を記録する。
4. `sources/manifest.json` に新しいファイルとSHA-256を追記する。既存スナップショットのハッシュを上書きして変更を隠さない。
5. 関連する要約・設計・判断を更新する。新旧どちらが有効か不明なら、両方を残し未確認とする。
6. 相対リンク、日付、出典ID、原文と引用の一致を確認する。

初版の `manifest.json` はユーザー全文から抜き出したファイルの元行範囲も保持しています。新しいWeb資料は同じ原文の行番号を持たないので、元全文との対応を捏造せず、URL・取得方法を別途記録します。

ハッシュ確認例（ファイル名を実際のものに置き換える）:

```sh
shasum -a 256 docs/sources/2026-10-17-user-input.txt
```

## 6. AIへ渡す依頼の雛形

```text
このリポジトリのAGENTS.mdと、そこから指定されている共有文書を読んでください。
今回の担当: ［機能・文書］
作業範囲: ［編集する場所・他担当との境界］
期待する成果物: ［具体的な結果］
検証: ［実機条件・入力例・期待する動作］
未決事項はSTATUS.md、採用した判断はDECISIONS.mdに根拠を残してください。
既存README.mdを変更しないという制約を守ってください。
```

Web上のチャットへ手動で資料を渡す場合は、少なくともAGENTS、AI_CONTEXT、STATUSと担当領域の文書を渡します。大会ルールを判定する作業では原文も必要です。原文だけで製品仕様を推測させず、入口と一緒に渡してください。

## 7. 提出資料への反映

ルートREADMEは大会が要求する提出形式です。今回の依頼では変更を禁止されているため、提出に必要な記入内容の一覧は `HACKATHON.md` に置いています。今ある共有資料の作成を、提出完了と扱わないでください。

Gitの差分・commit、使った外部素材、事前準備とHack Day中の独自実装を追える状態にします。原文アーカイブは参照資料として出典を保ち、製品の独自技術として数えないでください。
